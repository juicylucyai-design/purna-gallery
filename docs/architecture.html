Blueprint

Built in layers,
one module at a time

purnagallery.com launches as a coming-soon page, but it is built on the same skeleton the full gallery site will use. Every feature is a self-contained module, and every module is split into the same four layers. You can redesign a page, swap the database or change email providers without touching anything else.

The pattern

Layered MVC with feature modules

Classic MVC has three boxes, and in practice the business rules end up leaking into controllers or models until both are bloated. We keep MVC's View and Controller, then split the Model into two clear jobs: a Service that holds the rules, and a Repository that talks to storage. The code is also grouped by feature (waitlist, enquiry, content) rather than by type, so everything about one feature lives in one folder and can be changed or deleted in isolation.

Four rules

How we keep it from turning into spaghetti

Calls go down only

View → Controller → Service → Repository. A Service never imports a component; a Repository never calls a Service.

Modules meet at the front door

Each module exports one index.ts. Other modules import only from it, never from a file inside another module's folder.

Contracts are shared types

Request and response shapes live in contracts/index.d.ts. The form and the controller both import it, so they can't drift apart.

Outside systems sit behind interfaces

Services ask for a repository or an EmailSender, not Postgres or Resend. Tests pass in-memory stand-ins; production passes the real ones.

These rules are enforced by a lint check (dependency-cruiser, run as npm run check:boundaries), so a wrong import fails the build rather than waiting for code review.

One request, traced

A visitor taps "Notify me"

  1. ViewNotifyForm posts a WaitlistRequest (from contracts) through lib/api.ts.
  2. ControllerWaitlistController applies the rate limit, drops honeypot spam, normalises the email and calls subscribe(email).
  3. ServiceWaitlistService asks the repository to add the address and learns whether it is new.
  4. RepositoryOne INSERT ... ON CONFLICT DO NOTHING into waitlist_subscribers.
  5. Across modulesNew subscribers only: the Service calls welcomeSubscriber() on the Notification front door. How the email is sent is not its concern.
  6. Back upThe Controller returns 201. The View swaps the form for "Thank you. We'll write when the doors open."

When something breaks, the layer tells you where to look: a wrong status code is the Controller, a duplicate signup is the Service, a missing row is the Repository.
